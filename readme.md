**1. Архитектура анализа amoCRM и телефонии**

Для первой версии достаточно Python-сервиса, PostgreSQL и очереди фоновых задач. LLM-агент нужен для анализа разговоров и подготовки выводов. Сбор данных, расчёты и управление заданиями выполняются обычным кодом.

**Координатор** принимает запрос руководителя, проверяет доступ и фиксирует параметры отчёта: последние 30 дней, часовой пояс, воронки и менеджеров выбранного отдела. Затем запускает обработку.

**Модуль интеграций** получает сделки и задачи через amoCRM API v4 (`/api/v4/leads`, `/api/v4/tasks`), историю изменений — через `/api/v4/events`, пользователей и этапы — из справочников. Звонки и записи поступают через API подключённой телефонии. Приоритет имеет готовая связь звонка со сделкой; сопоставление по номеру, контакту и времени используется, если такой связи нет. Неоднозначные совпадения передаются человеку.

Все обращения к amoCRM проходят через общий для фоновых задач ограничитель частоты запросов. OAuth-модуль обновляет токены и сохраняет новую пару access/refresh token под блокировкой, чтобы несколько задач не обновляли её одновременно. После первоначальной загрузки сохраняются изменения через вебхуки и периодическую сверку API, без полного скачивания аккаунта для каждого отчёта.

**Обработка звонков** состоит из распознавания речи с таймкодами и разделения участников. Для двухканальной записи используются каналы телефонии, для общей — отдельный модуль определения говорящих. LLM-агент сопоставляет расшифровку с правилами продаж и возвращает тип замечания, объяснение и `segment_ids` — идентификаторы подтверждающих фрагментов. Сервер проверяет их принадлежность звонку и сам извлекает цитату, говорящего и время из исходных сегментов.

В отчёте у каждого замечания есть ссылка на сделку и кнопка **«Прослушать фрагмент»**. Плеер открывает нужный момент исходной записи; рядом доступны контекст и весь разговор. Руководитель может подтвердить или отклонить замечание. Это позволяет проверить и расшифровку, и вывод модели.

**Расчёты и отчёт.** Python/SQL считает сделки, их суммы и задачи. Определения показателей фиксируются в настройках: например, доля успешных среди закрытых — число успешно закрытых за период, делённое на общее число успешно и неуспешно закрытых за тот же период. Правила отнесения сделок к менеджерам также фиксируются заранее. LLM объясняет рассчитанные показатели и связывает их с замечаниями по звонкам. Результаты за 30 дней и текущие проблемные сделки показываются отдельно; старые открытые сделки не исключаются.

Данные CRM, расшифровки и отчёты хранятся в PostgreSQL, аудио — в закрытом S3-совместимом хранилище. Вместе с замечанием сохраняются использованные ответы API и время их получения. Перед включением проблемы с задачей в отчёт сделка и её задачи перечитываются. Это снижает риск устаревшего вывода, но не создаёт единого снимка CRM: данные могут меняться между запросами. Доступ к записи проверяется при открытии; после окончания согласованного срока хранения в отчёте отмечается её недоступность.

Запуск — с одной воронки: сверка цифр и ручная проверка выборки звонков, затем расширение на отдел.

**2. Что система делает сама, а что передаёт человеку**

Система собирает данные, расшифровывает звонки, рассчитывает показатели и готовит отчёт. Просрочки и отсутствие задач определяются правилами; замечания по содержанию разговоров предлагаются для проверки руководителю.

На старте интеграция работает только на чтение. После пилота можно включить создание задач и напоминаний по утверждённым правилам, с журналом действий, повторной проверкой актуальности и защитой от дублей. Спорные выводы, решения по клиентам и оценка сотрудников остаются за человеком.

Основные риски:

1. **Неполные данные.** Не все звонки имеют запись или однозначную связь со сделкой. Такие пробелы отмечаются в отчёте, спорные связи проверяются вручную. Отсутствие записи не означает, что разговора не было.
2. **Ошибки в анализе.** Модель может неверно понять разговор. Поэтому замечания сопровождаются ссылками на фрагменты записи, а перед запуском результаты сверяются с ручным разбором звонков.
3. **Безопасность данных.** Доступ к записям ограничивается правами сотрудников. Модуль анализа не может менять сделки. Использование внешнего AI-сервиса и сроки хранения записей согласуются с компанией.


**3. Выборка сделок из amoCRM**

Область проверки задаётся ID воронки и списком ответственных менеджеров. Выбираются открытые сделки без незавершённых задач либо с хотя бы одной просроченной задачей. Выполненные задачи не учитываются; будущая задача не отменяет старую просрочку. Дата создания сделки не ограничивается.

Задачи загружаются пакетами только для выбранных сделок. Перед добавлением найденной проблемы в результат повторно запрашиваются сама сделка и её незавершённые задачи. В выборку входят задачи, привязанные непосредственно к сделке; полнота результата зависит от прав интеграции.

Код работает в одном процессе с готовым access token. Получение и обновление токенов — в отдельном модуле. Для работы нужны серверные фильтры amoCRM.

```python
import json, os, time
from itertools import islice
import requests
from requests.adapters import HTTPAdapter
from urllib3.util.retry import Retry
BASE = f"https://{os.environ['AMO_SUBDOMAIN']}.amocrm.ru/api/v4"
session = requests.Session()
session.headers['Authorization'] = f"Bearer {os.environ['AMO_ACCESS_TOKEN']}"
retry = Retry(total=4, backoff_factor=1, allowed_methods={'GET'},
              status_forcelist=[429, 500, 502, 503, 504], respect_retry_after_header=True)
session.mount('https://', HTTPAdapter(max_retries=retry))
def fetch_all(entity, **filters):
    page = 1
    while True:
        time.sleep(0.2)
        response = session.get(f'{BASE}/{entity}', timeout=(5, 30),
                               params=dict(filters, limit=250, page=page))
        response.raise_for_status()
        if response.status_code == 204:
            return
        data = response.json()
        yield from data['_embedded'][entity]
        if not data.get('_links', {}).get('next'):
            return
        page += 1
def find_problem_leads(pipeline_id, owner_ids):
    scope = {'filter[pipeline_id]': pipeline_id, 'filter[responsible_user_id][]': owner_ids}
    leads = (x for x in fetch_all('leads', **scope) if x['status_id'] not in {142, 143})
    result = {}
    while batch := list(islice(leads, 50)):
        filters = {'filter[entity_type]': 'leads', 'filter[is_completed]': 0,
                   'filter[entity_id][]': [x['id'] for x in batch]}
        tasks, now = list(fetch_all('tasks', **filters)), int(time.time())
        for lead in batch:
            pending = [t for t in tasks if t['entity_id'] == lead['id']]
            if pending and all(t['complete_till'] >= now for t in pending):
                continue
            current = next(fetch_all('leads', **scope, **{'filter[id]': lead['id']}), None)
            if not current or current['status_id'] in {142, 143}:
                continue
            filters['filter[entity_id][]'] = [lead['id']]
            fresh, now = list(fetch_all('tasks', **filters)), int(time.time())
            overdue = [t['id'] for t in fresh if t['complete_till'] < now]
            if not fresh or overdue:
                result[lead['id']] = dict(id=lead['id'], name=current['name'],
                                         no_open_tasks=not fresh, overdue_task_ids=overdue, checked_at=now)
    return list(result.values())
if __name__ == '__main__':
    owners = [int(x) for x in os.environ['AMO_USER_IDS'].split(',')]
    print(json.dumps(find_problem_leads(int(os.environ['AMO_PIPELINE_ID']), owners), ensure_ascii=False))
```

На этапе сегментации удалось повысить скорость тяжёлой модели на RTX 3060 с 2,8 до 4,9 пары кадров в секунду за счёт пакетной обработки. Это замер конкретного этапа на двух камерах; качество трекинга проверялось отдельно по ручной разметке.

На вход подавалась обычная картинка плана, на выходе получался JSON со стенами, их толщиной, дверями, окнами и контурами комнат. Для этого я освоил подготовку обучающих данных из SVG-разметки, обучение моделей на Python и PyTorch и преобразование результатов распознавания в векторную геометрию. Пришлось разбираться, как соединять участки стен, сохранять углы и привязывать двери и окна к нужной стене. Например, угловое окно программа сначала пыталась описать одним прямоугольником, из-за чего теряла его форму. После изменения этой обработки и объединения результатов пяти прогонов пиксельный F1 по окнам вырос с 0,900 до 0,959 без переобучения модели. Сравнение проводилось на 200 проверочных планах, на масках 256 × 256 с допуском один пиксель. Это рабочая валидация: параметры обработки подбирались на той же выборке.

В проекте видеоаналитики я отдельно разобрался с синхронизацией камер и сопоставлением одного человека на разных записях. Применил модели, которые сравнивали признаки внешности, и проверял, где система путала людей или теряла их при переходе между камерами. Также освоил обучение на удалённых GPU через Kaggle и Colab, организацию очередей заданий и сохранение результатов.
